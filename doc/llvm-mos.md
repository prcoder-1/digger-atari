# llvm-mos для порта Digger: замеры и разведка

Сентябрь 2026. Вопрос был такой: даёт ли llvm-mos выигрыш по размеру кода
против cc65 и можно ли на него переехать. Замеры сделаны на нашем коде,
разведка доведена до работающей программы. Исходники разведки лежат рядом,
в `doc/spike-llvm-mos/`.

## Сколько даёт

Десять модулей на Си, собранных `mos-clang -Oz`, против сегмента CODE у cc65
(cc65 уже с `-Cl`, то есть в своей лучшей форме):

| модуль | cc65 | llvm-mos | |
| --- | ---: | ---: | ---: |
| `bags.c` | 4012 | 3103 | −23% |
| `bugs.c` | 3532 | 2787 | −21% |
| `screen.c` | 1016 | 757 | −25% |
| `text.c` | 520 | 427 | −18% |
| `field.c` | 2710 | 2408 | −11% |
| `man.c` | 1751 | 1649 | −6% |
| `main.c` | 1556 | 1626 | +4% |
| `missile.c` | 1066 | 1101 | +3% |
| `hud.c` | 154 | 174 | +13% |
| `sfx.c` | 570 | 651 | +14% |
| **итого** | **16887** | **14683** | **−13%** |

Это около 2,2 КБ, то есть примерно десятая часть всего CODE (остальное -
ассемблерные модули, их замер не касается).

Выигрыш собран на крупных модулях и ровно там, где cc65 выдыхается: работа со
структурами в массиве. На мелких модулях llvm-mos местами проигрывает.

## Почему так выходит

Из ветки разработки бэкенда на 6502.org (`viewtopic.php?f=2&t=6450`, автор
mysterymath): нулевая страница используется как регистровый файл (мнимые
регистры `__rc0..__rc31`, понижаемые в реальную память поздним проходом);
нерекурсивные функции получают статические кадры по анализу графа вызовов -
то же, что у cc65 даёт `-Cl`, но выводится, а не разрешается флагом на весь
проект; сквозная оптимизация при линковке; распознавание индексов циклов под
индексную адресацию. Слабые места автор называет сам: многобайтные сравнения
(EOR всех байт) и то, что приоритеты LLVM вообще не про 6502 - берут
количеством проходов (около сотни, из них восемь своих).

На нашей `bags_blocked` разница видна прямо в выводе:

```
.LBB3_2: cmp #56          ; 7 мешков по 8 байт - шаг известен
         lda bags,x       ; прямая индексная выборка поля
```

против cc65, где перед КАЖДЫМ обращением к полю идёт `jsr mulax6`, `jsr
pushax` и чтение указателя из кадра через `lda (sp),y`.

## Разведка: ОЗУ под ПЗУ

Главное неизвестное было не в кодогенерации, а в раскладке памяти. Весь порт
держится на цели cc65 `atarixl`: выключение ПЗУ через PORTB, промежуточная
область `SRPREPCHNK` и перенос `SHADOW_RAM` стартовым кодом библиотеки. У
llvm-mos платформа `atari8` описывает просто плоское ОЗУ $2000..$C000 одним
сегментом XEX, ничего подобного там нет.

**Итог разведки: работает.** Программа кладёт восемь известных байт в секцию с
адресом исполнения $E400 и адресом загрузки в обычном ОЗУ, стартовый код
выключает ПЗУ и переносит их, затем `main` сверяет и красит границу экрана:
зелёная - доехало, красная - нет.

Контрольный опыт обязателен и сделан: та же сборка с ВЫКЛЮЧЕННЫМ переносом
даёт красную границу. Без него зелёный цвет ничего не доказывал бы.

```
перенос включён    граница #3a6b00 (зелёная, COLBK=$C6)
перенос выключен   граница #84313a (красная,  COLBK=$36)
```

Устройство получилось чище, чем у cc65:

* раздельные адреса загрузки и исполнения - штатные, `>hidden AT>ram` в
  link-скрипте, символы `LOADADDR`/`ADDR`/`SIZEOF` линковщик даёт сам;
* своё действие при старте вставляется секцией `.init.50` - цепочка
  инициализации приоритетная, штатная инициализация мягкого стека сидит в
  `.init.100`;
* заголовок XEX собирается руками в блоке `OUTPUT_FORMAT`, так что при нужде
  можно выпустить и многосегментный файл.

## Четыре ловушки, каждая стоила времени

1. **В секции `.init.*` НЕЛЬЗЯ ставить `rts`.** Они идут сквозным потоком, одна
   за другой, и никто их не вызывает - в штатной `init-stack.S` возврата тоже
   нет. Поставленный `rts` снимает со стека чужой адрес и уводит управление в
   никуда: `main` не отрабатывает вовсе, а выглядит это как «программа не
   запускается».

2. **Секция с `AT>ram` обязана лежать МЕЖДУ `rodata` и `data`.** Если положить
   её после `INCLUDE c.ld`, её адрес загрузки уезжает за `.bss`: та `NOLOAD`,
   но место в регионе занимает. Адрес оказывается за концом загружаемого
   образа, и переносить нечего. Признак: заголовок XEX обещает 591 байт при
   файле в 472.

3. **LTO выбрасывает `const`-данные вместе с секцией.** Оптимизатор
   подставляет содержимое массива прямо в сравнение и удаляет сам массив;
   секция выходит нулевого размера, и проверка становится бессмысленной.
   Лечится `volatile`. Переименование секции (пробовал `.hidden` -> `.romdata`)
   НЕ помогает - дело не в имени.

4. **Цвет фона на экране проверять через теневую ячейку $02C8, а не COLBK.**
   Пока ПЗУ включено, VBI операционной системы каждый кадр льёт тень в
   регистр, и прямая запись в $D01A живёт меньше кадра. После выключения ПЗУ и
   гашения NMIEN - наоборот, работает только прямая запись. На этом легко
   решить, что программа не запустилась.

Отдельно: **SDK в поставке - только исходное дерево платформ.** Готовых
библиотек и link-скриптов в дереве компилятора нет, линковать нечем, пока не
собрать и не установить:

```
cd ~/ATARI/llvm-mos-sdk/build && make common atari8-common atari8
cmake --install . --prefix <куда-нибудь>
```

## Что осталось, если переезжать всерьёз

Разведка сняла главный риск, но не работу. Осталось:

1. **Ассемблерный слой** - 1709 строк рукописного (`blit.s` с самомодификацией
   и макросами, `vbi.s`, `dli.s`, `music.s`, `pokey.s`, `pmg.s`, `score.s`,
   `util.s`, `scrmem.s`, `pmgmem.s`) плюс 3431 строки генерируемого. Второе не
   страшно: его выдают наши же скрипты в `tools/`, там меняется вывод.
2. **Стык Си с ассемблером по нулевой странице.** У нас параметры блиттера и
   PMG передаются через именованные ячейки, объявленные в `.s` и втянутые в Си
   через `#pragma zpsym`. У llvm-mos нулевая страница занята мнимыми
   регистрами ($80..$9F при `-mlto-zp=96`), и раскладку надо развести.
3. **Полный link-скрипт**: кадровый буфер по $9000 с выравниванием на 4К,
   дисплей-лист, таблицы строк, буфер PMG с выравниванием на 2К и три области
   под ПЗУ.
4. **Приёмка** - `tools/check.sh` обязан дать те же байты телеметрии. Инструмент
   уже есть, и это единственная честная проверка такого переезда.

Дешёвая альтернатива, которую стоит взвесить рядом: зеркалирование спрайтов на
cc65 освобождает 900-1800 байт под ПЗУ, куда уезжают `LEVELS` (640 байт) и
часть RODATA. Выигрыш для MAIN сопоставим с llvm-mos, а инструментарий трогать
не надо.

# llvm-mos для порта Digger: замеры и разведка

Сентябрь 2026. Вопрос был такой: даёт ли llvm-mos выигрыш по размеру кода
против cc65 и можно ли на него переехать. Замеры сделаны на нашем коде,
разведка доведена до работающей программы. Исходники разведки лежат рядом,
в `doc/spike-llvm-mos/`.

## Сколько даёт

Десять модулей на Си, собранных `mos-clang -Oz`, против сегмента CODE у cc65
(cc65 уже с `-Cl`, то есть в своей лучшей форме):

| модуль | cc65 | llvm-mos | |
| --- | ---: | ---: | ---: |
| `bags.c` | 4012 | 3103 | −23% |
| `bugs.c` | 3532 | 2787 | −21% |
| `screen.c` | 1016 | 757 | −25% |
| `text.c` | 520 | 427 | −18% |
| `field.c` | 2710 | 2408 | −11% |
| `man.c` | 1751 | 1649 | −6% |
| `main.c` | 1556 | 1626 | +4% |
| `missile.c` | 1066 | 1101 | +3% |
| `hud.c` | 154 | 174 | +13% |
| `sfx.c` | 570 | 651 | +14% |
| **итого** | **16887** | **14683** | **−13%** |

Это около 2,2 КБ, то есть примерно десятая часть всего CODE (остальное -
ассемблерные модули, их замер не касается).

Выигрыш собран на крупных модулях и ровно там, где cc65 выдыхается: работа со
структурами в массиве. На мелких модулях llvm-mos местами проигрывает.

## Почему так выходит

Из ветки разработки бэкенда на 6502.org (`viewtopic.php?f=2&t=6450`, автор
mysterymath): нулевая страница используется как регистровый файл (мнимые
регистры `__rc0..__rc31`, понижаемые в реальную память поздним проходом);
нерекурсивные функции получают статические кадры по анализу графа вызовов -
то же, что у cc65 даёт `-Cl`, но выводится, а не разрешается флагом на весь
проект; сквозная оптимизация при линковке; распознавание индексов циклов под
индексную адресацию. Слабые места автор называет сам: многобайтные сравнения
(EOR всех байт) и то, что приоритеты LLVM вообще не про 6502 - берут
количеством проходов (около сотни, из них восемь своих).

На нашей `bags_blocked` разница видна прямо в выводе:

```
.LBB3_2: cmp #56          ; 7 мешков по 8 байт - шаг известен
         lda bags,x       ; прямая индексная выборка поля
```

против cc65, где перед КАЖДЫМ обращением к полю идёт `jsr mulax6`, `jsr
pushax` и чтение указателя из кадра через `lda (sp),y`.

## Разведка: ОЗУ под ПЗУ

Главное неизвестное было не в кодогенерации, а в раскладке памяти. Весь порт
держится на цели cc65 `atarixl`: выключение ПЗУ через PORTB, промежуточная
область `SRPREPCHNK` и перенос `SHADOW_RAM` стартовым кодом библиотеки. У
llvm-mos платформа `atari8` описывает просто плоское ОЗУ $2000..$C000 одним
сегментом XEX, ничего подобного там нет.

**Итог разведки: работает.** Программа кладёт восемь известных байт в секцию с
адресом исполнения $E400 и адресом загрузки в обычном ОЗУ, стартовый код
выключает ПЗУ и переносит их, затем `main` сверяет и красит границу экрана:
зелёная - доехало, красная - нет.

Контрольный опыт обязателен и сделан: та же сборка с ВЫКЛЮЧЕННЫМ переносом
даёт красную границу. Без него зелёный цвет ничего не доказывал бы.

```
перенос включён    граница #3a6b00 (зелёная, COLBK=$C6)
перенос выключен   граница #84313a (красная,  COLBK=$36)
```

Устройство получилось чище, чем у cc65:

* раздельные адреса загрузки и исполнения - штатные, `>hidden AT>ram` в
  link-скрипте, символы `LOADADDR`/`ADDR`/`SIZEOF` линковщик даёт сам;
* своё действие при старте вставляется секцией `.init.50` - цепочка
  инициализации приоритетная, штатная инициализация мягкого стека сидит в
  `.init.100`;
* заголовок XEX собирается руками в блоке `OUTPUT_FORMAT`, так что при нужде
  можно выпустить и многосегментный файл.

## Четыре ловушки, каждая стоила времени

1. **В секции `.init.*` НЕЛЬЗЯ ставить `rts`.** Они идут сквозным потоком, одна
   за другой, и никто их не вызывает - в штатной `init-stack.S` возврата тоже
   нет. Поставленный `rts` снимает со стека чужой адрес и уводит управление в
   никуда: `main` не отрабатывает вовсе, а выглядит это как «программа не
   запускается».

2. **Секция с `AT>ram` обязана лежать МЕЖДУ `rodata` и `data`.** Если положить
   её после `INCLUDE c.ld`, её адрес загрузки уезжает за `.bss`: та `NOLOAD`,
   но место в регионе занимает. Адрес оказывается за концом загружаемого
   образа, и переносить нечего. Признак: заголовок XEX обещает 591 байт при
   файле в 472.

3. **LTO выбрасывает `const`-данные вместе с секцией.** Оптимизатор
   подставляет содержимое массива прямо в сравнение и удаляет сам массив;
   секция выходит нулевого размера, и проверка становится бессмысленной.
   Лечится `volatile`. Переименование секции (пробовал `.hidden` -> `.romdata`)
   НЕ помогает - дело не в имени.

4. **Цвет фона на экране проверять через теневую ячейку $02C8, а не COLBK.**
   Пока ПЗУ включено, VBI операционной системы каждый кадр льёт тень в
   регистр, и прямая запись в $D01A живёт меньше кадра. После выключения ПЗУ и
   гашения NMIEN - наоборот, работает только прямая запись. На этом легко
   решить, что программа не запустилась.

Отдельно: **SDK в поставке - только исходное дерево платформ.** Готовых
библиотек и link-скриптов в дереве компилятора нет, линковать нечем, пока не
собрать и не установить:

```
cd ~/ATARI/llvm-mos-sdk/build && make common atari8-common atari8
cmake --install . --prefix <куда-нибудь>
```

## Вторая разведка: ассемблерный слой и стык по нулевой странице

Следующий по величине риск после ОЗУ под ПЗУ. Взят самый тяжёлый файл порта -
`src/blit.s`: самомодификация операндов, макрос, параметры в именованных
ячейках нулевой страницы. Перенесены `blit_mask` и `clear_px`, проверка
функциональная - тот же вывод считается и перенесённой процедурой, и простой
реализацией на Си, результаты сравниваются побайтно. Исходники в
`doc/spike-llvm-mos/blit/`.

**Итог: работает.** Контрольный опыт (перенесённая процедура заменена на
пустую) даёт другой цвет, то есть проверка настоящая.

Перенос оказался механическим:

| ca65 | llvm-mos |
| --- | --- |
| `.segment "ZEROPAGE"` | `.section .zp.bss,"aw",@nobits` плюс `.zeropage имя` |
| `.export` / `.import` | `.globl` |
| `.macro` / `.endmacro`, параметры `op1` | `.macro` / `.endm`, параметры `\op1` |
| `.res N` | `.zero N` |
| `_имя` для символов из Си | `имя`, без ведущего подчёркивания |

Что важно и не было очевидно:

* **самомодификация переносится дословно** - она про машину, а не про
  ассемблер;
* директива `.zeropage` заставляет ассемблер брать ОДНОБАЙТНУЮ адресацию для
  символа, чей адрес известен только линковщику. Это ровно то, ради чего у нас
  в заголовках стоит `#pragma zpsym`, - у llvm-mos аналог не нужен, из Си
  ячейки видны обычным `extern`;
* линковщик сам разводит наши ячейки с мнимыми регистрами: те заняли
  $80..$9F, наши легли с $A2. Руками раскладывать нулевую страницу не
  пришлось.

Ловушка, общая для таких проверок: **буферы, чьи адреса уходят в ассемблер
через таблицы строк как ЧИСЛА, обязаны быть `volatile`.** Оптимизатор LLVM не
обязан считать, что внешняя процедура их меняет, и сравнение свернётся в
константу - проверка станет бессмысленной, как и в первой разведке с
`const`-массивом.

## Третья разведка: прерывания и свои векторы

Наши `vbi.s` и `dli.s` ставят себя в аппаратные векторы. С выключенным ПЗУ
векторы 6502 по $FFFA..$FFFF лежат в обычном ОЗУ, то есть принадлежат нам -
ровно на этом держится порт на cc65. Проверялось, можно ли этим пользоваться
из программы, собранной llvm-mos.

Разведка ставит свой обработчик вертикального гашения прямо в $FFFA, включает
NMIEN и считает кадры в ячейке нулевой страницы; `main` на Си читает счётчик и
зеленит границу, когда тот перевалит за сотню. Исходники в
`doc/spike-llvm-mos/irq/`.

**Итог: работает.** Контрольный опыт с невключённым NMIEN оставляет границу
красной, то есть зелёный цвет действительно от обработчика.

Заодно видно, что регион под ПЗУ надо кончать на $FFF9, оставляя последние
шесть байт векторам, - в нашем cc65-конфиге `HIDDEN_RAM` кончается там же и по
той же причине.

## Что осталось, если переезжать всерьёз

Обе разведки сняли риски, но не работу. Осталось:

1. **Перенести ассемблер** - 1709 строк рукописного плюс 3431 строки
   генерируемого. Работа объёмная, но после проверки на `blit.s` уже не
   рискованная: правила перевода в таблице выше, и самый сложный файл по ним
   переносится дословно. Генерируемое не страшно вовсе - его выдают наши же
   скрипты в `tools/`, там меняется вывод.
2. **Полный link-скрипт**: кадровый буфер по $9000 с выравниванием на 4К,
   дисплей-лист, таблицы строк, буфер PMG с выравниванием на 2К и три области
   под ПЗУ. Механизм проверен на одной области, остальные - то же самое.
3. **Приёмка** - `tools/check.sh` обязан дать те же байты телеметрии. Инструмент
   уже есть, и это единственная честная проверка такого переезда.

## Дешёвая альтернатива взвешена и почти отпала

Рядом всё время стояло другое предложение: зеркалировать спрайты на лету, как
в порте на БК, и освободившееся под ПЗУ место отдать под `LEVELS` (640 байт) и
часть RODATA. Замерено по данным - выходит хуже, чем казалось.

Левые кадры Диггера **не все** являются зеркалом правых: из шести точное
зеркало дают четыре, а `l1` и `l5` художник нарисовал отдельно - расходятся
шесть байт из шестидесяти, и это не сдвиг, а другой рисунок колёс. У пары
"вниз из вверх" (зеркало по обеим осям, как на БК) точных только два кадра из
шести.

| | сэкономить | заплатить | чисто |
| --- | ---: | ---: | ---: |
| зеркало 4 кадров "влево" и 2 "вниз" | 900 | 256 таблица + ~100 код | **544** |
| для сравнения: флаг `-Cl` | | | 990 |

Пятьсот байт ценой смешанной схемы, где часть кадров зеркалится, а часть
лежит как есть, - плохая сделка. Брать зеркало и для несовпадающих кадров
нельзя: расходятся ровно средние фазы анимации, это будет видно.

Вывод: дешёвого резерва такого размера у нас больше нет, и llvm-mos с его 2,2
КБ остаётся единственным существенным рычагом.

## Переезд сделан

Игра собирается llvm-mos и проходит приёмку: телеметрия демо-прогона совпадает
с эталоном cc65 **байт в байт** за 252 такта - такт, счёт, положение Диггера,
камни, мешки, враги, жизни, выстрелы, уровень, счётчики звука, бонус-режим и
положение первого врага.

```
cc65 CODE      21507
llvm-mos .text 16836        -4671 байт, -21,7%
XEX            35902 -> 28458
```

Выигрыш вышел вдвое больше помодульного замера (тот обещал 2,2 КБ на коде Си):
разницу дала сквозная оптимизация при линковке, которую помодульное измерение
поймать не могло.

Обе сборки идут ИЗ ОДНОГО исходника. Ассемблер не дублируется - файлы
`src/*.s` и `assets/*.s` переводит `tools/ca65_to_mos.py`. Различия в Си
собраны в `src/compat.h` и в рамках `#ifdef __CC65__` вокруг прагм cc65.

### Что пришлось написать заново

Цель cc65 `atarixl` даёт больше, чем видно по конфигу, и на это опирается вся
игра. Замером выяснено: ПЗУ ОС выключено (PORTB = $FE), по $E462 лежат наши
спрайты, а вектор NMI указывает на $25xx - то есть **cc65 подставляет вместо
обработчика ОС свою заглушку в низкой памяти**. Игра пользуется ей насквозь:
`screen.c` ставит дисплей-лист записью в ТЕНЕВУЮ ячейку SDLSTL, палитра идёт
через COLOR0..COLOR4, джойстик читается из STICK0, `dli.s` вешается на VDSLST,
`vbi.s` - на VVBLKD и выходит через XITVBV.

Поэтому в `mos/` лежат три файла:

* `link.ld` - раскладка. Образы спрайтов КЛАДУТСЯ при загрузке в кадровый
  буфер и буфер игроков: в этот момент те ещё пусты, а в основном ОЗУ девяти
  килобайт нет. Области загрузки заведены отдельными регионами, иначе счётчик
  региона съедает место у самого буфера.
* `init.S` - выключение ПЗУ, сохранение знакогенератора и перенос спрайтов.
* `nmi.S` - заглушка вместо обработчика ОС: часы, перенос теней в регистры,
  защёлка джойстика, раздача по VDSLST и VVBLKD, выход вместо XITVBV.

### Три ошибки, стоившие времени

1. **Мягкий стек Си ставился от MEMTOP** (~$9C00) штатной `init-stack.S` и рос
   вниз прямо по кадровому буферу с $9000. Экран оставался чёрным, и это не
   выглядело как проблема стека. Лечится своей секцией `.init.150` - она идёт
   после штатной `.init.100`.
2. **Знакогенератор**. `text_char` берёт буквы из ПЗУ по $E000 (надпись GAME
   OVER). Спасается копией самого в себя, пока ПЗУ ещё включено: чтение идёт
   из ПЗУ, запись по тому же адресу - в ОЗУ под ним.
3. **Указатели в нулевой странице до обнуления .bss**. Секция `.init.50` идёт
   РАНЬШЕ `.init.200`, где чистится bss, поэтому все ячейки в ней надо ставить
   явно - и младшие байты тоже.

### Клавиатура

У ОС клавиатуру обслуживает прерывание IRQ: оно ловит нажатие, гасит дребезг и
кладёт код в ячейку CH ($02FC). У нас IRQ маскированы - ПЗУ выключено, и
обработчику ОС взяться неоткуда, - поэтому клавиатура ОПРАШИВАЕТСЯ в кадровом
прерывании, в `mos/nmi.S`: бит 2 в SKSTAT снят, пока клавиша нажата, и тогда
код из KBCODE кладётся в CH.

Выходит даже лучше, чем у ОС: пока клавиша прижата, код обновляется каждый
кадр, а игра его забирает и ставит обратно $FF (`key_dir` в `main.c`). То есть
удержание работает без задержки автоповтора - у ОС первое повторение приходит
через полсекунды, и Диггер дёргался бы.

**Проверено настоящим нажатием**, а не рассуждением. Для этого понадобились две
новые вещи, которых в харнессе не было вовсе:

* сборка `-DDIGGER_DEMO -DDEMO_KEYS` - ввод берётся с клавиатуры и джойстика, а
  телеметрия остаётся;
* `tools/keytest.sh` - запускает XEX, УДЕРЖИВАЕТ клавишу через xdotool и снимает
  кадр.

```
llvm-mos  без клавиши y=190, с удержанием "-" y=103
cc65      без клавиши y=190, с удержанием "-" y=124
```

Диггер стартует в ряду 9 (y=190) и поднимается. Разница между сборками - только
скорость кода.

### Ловушка харнесса: чужой эмулятор на том же дисплее

`shot.sh` держал эмулятор на дисплее :99 и добивал прошлый запуск через
`pkill -x atari800`. Пока проект был один, это работало. Стоило на той же
машине запуститься эмулятору СОСЕДНЕГО проекта - и вышло сразу две беды: снимок
брался с чужого окна и выходил пустым (выглядело как поломка игры, я успел
дважды получить ложное "РАСХОЖДЕНИЕ"), а `pkill` по имени процесса глушил чужую
работу.

Теперь у проекта свой дисплей (`DIGGER_DISPLAY`, по умолчанию :97), а свой
эмулятор добивается по номеру процесса из `PIDFILE`, а не по имени.

### Что осталось незакрытым

* **Замер размера делался на clang 18**, а сборка SDK подтянула более свежий
  компилятор. Цифры выше сняты с того, чем собрано сейчас.
